## Steady state: secrets live in 1Password

After [Provisioning with OpenTofu](/topics/provisioning-with-tofu/) or a manual bootstrap, the file on the VPS is:

```
~/infra/compose/compose/.env.production
```

Permissions `0600`, contents look like:

```ini
POSTGRES_PASSWORD=op://Production/Postgres/password
JWT_SECRET=op://Production/Auth/jwt_secret
GOOGLE_OAUTH_CLIENT_SECRET=op://Production/OAuth/google_client_secret
STRIPE_SECRET_KEY=op://Production/Stripe/secret_key
WUD_GHCR_TOKEN=op://Production/GHCR/token
RESEND_API_KEY=op://Production/Email/resend_api_key
# ...one line per variable
```

Nothing in this file is a secret — it's a manifest of references. You can commit a redacted copy to a private mirror or share it on Slack without thinking. The actual values live in the **`Production` 1Password vault**, accessed by a [service-account token](https://developer.1password.com/docs/service-accounts) scoped to that one vault.

`op` resolves each `op://` URI by hitting the 1Password API once, hands the expanded env to the docker compose subprocess, and exits. No values touch the filesystem. No values touch the shell history.

For convenience, the `compose-up.sh` wrapper detects an `OP_SERVICE_ACCOUNT_TOKEN` in the environment and prefixes the docker compose call with `op run` automatically.

## What Postgres backups do _not_ cover

Nightly Postgres dumps (see [Backups](/runbooks/backups/)) capture database rows only. They do **not** include the 1Password vault or any secret material. That's the point: secrets and data live in separate stores, restored independently.

If you restore Postgres without the 1Password vault, the database comes back but the app can't sign cookies, hash passwords, or call any external API. Conversely, losing the vault doesn't lose your data — Postgres still has every row.

**Back up the 1Password vault itself** the way 1Password recommends: emergency kit printed and stored offline, multiple vault administrators, account recovery enabled.

## Rotation cadence

Rotating a secret in this model is: edit the 1Password item, restart the container. No SSH, no `vi`, no scp.

| Secret               | Cadence                  | Notes                                      |
| -------------------- | ------------------------ | ------------------------------------------ |
| `JWT_SECRET`         | On compromise only       | Rotating invalidates all sessions          |
| `POSTGRES_PASSWORD`  | Annual                   | Update vault + `ALTER USER` together       |
| OAuth client secrets | When provider prompts    | Rotate at provider, then in 1Password      |
| `WUD_GHCR_TOKEN`     | 90 days                  | PAT with `read:packages` scope             |
| Email API tokens     | Per provider policy      | Cloudflare / Resend / SendGrid dashboards  |

After every rotation:

1. Update the value in 1Password.
2. On the VPS: `op run --env-file=.env.production -- docker compose --profile prod up -d`.
3. The container restarts with the freshly resolved value.

Always provision the new value at the provider **before** revoking the old one, so traffic mid-rotation doesn't fail.

## Team handoff

When adding an operator:

1. Add them to the **`Production` 1Password vault** with read-only access (or read-write if they need to rotate).
2. Grant SSH access separately (see [Firewall & TLS](/runbooks/firewall-and-tls/)).
3. Share the `op-run-stack.sh` wrapper or document the boot command in your team wiki.

When offboarding: remove them from the 1Password vault. The service-account token on the host stays valid; rotate only the secrets they could have read locally during their tenure (which should be none, if they only had vault access).

## Break-glass disk backup

Useful only in narrow situations — e.g. you're auditing what a specific historical deploy used, or you need an air-gapped recovery procedure that doesn't require 1Password to be reachable.

To generate a one-time resolved copy:

```bash
# On the VPS, do NOT leave the output file in place after use.
op run --env-file=.env.production -- env | grep -v '^OP_' > /tmp/resolved.env
chmod 600 /tmp/resolved.env

# Encrypt it with age before moving anywhere:
age -r <your-age-public-key> /tmp/resolved.env > resolved.env.age
shred -u /tmp/resolved.env
```

Treat the `.age` file like a long-term backup tape: encrypted, off-host, recoverable only with the matching private key. Delete the plaintext immediately after.

  eyebrow="Hard rule"
  title="No raw values on disk for longer than one command"

>
  If you ever need to dump resolved values for debugging or recovery,
  redirect into a tmpfs, encrypt with age before persisting, and shred the

## FAQ

<FaqGroup>
  <FaqItem title="Can I use Bitwarden / Vault / Doppler / SOPS instead?" open>
    Yes. See [Secrets management → Alternatives](/infra/secrets/#alternatives).
    The flow shape is identical: references on disk, CLI resolves at boot.
  </FaqItem>
  <FaqItem title="What if 1Password is down when I need to restart?">
    `op` caches a service-account token's vault contents for a short window
    after a successful run. For longer outages, the break-glass disk backup
    above gives you a recovery path. Plan + drill it the way you drill DB
    restores.
  </FaqItem>
  <FaqItem title="Can I commit .env.production to a private git repo?">
    Yes — it's just references, no secret values. Many teams do this so the
    boot manifest is versioned alongside the code. Treat the repo as the
    truth-of-references; the 1Password vault as the truth-of-values.
  </FaqItem>
  <FaqItem title="Do I need this for local dev?">
    Optional. [Secrets management → Local dev](/infra/secrets/#local-dev)
    covers the `op run --env-file=.env.local` pattern. Solo devs running
    Compose locally can fall back to raw `.env` — never in production.
  </FaqItem>
</FaqGroup>
