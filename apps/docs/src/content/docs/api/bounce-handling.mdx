  verified user always starts fresh.

## Per-provider model

Each provider tracks deliverability differently. The API maps all three onto
a single local table so the dispatch path looks the same regardless of which
provider is active.

Cloudflare is the default for the API template. Its API refuses sends to
addresses on Cloudflare's own list, so the local mirror is a performance
hint, not a correctness requirement. Resend and SendGrid leave the
blocklist entirely to the application, the webhooks are how their
verdict reaches us.

## How the dispatch path uses it

```mermaid
flowchart LR
  caller["sendTemplate(...)"] --> check{isSuppressed(to)?}
  check -- yes --> short["mark delivery suppressed<br/>skip provider"]
  check -- no --> provider["provider.send()"]
  provider -- success --> sent["mark delivery sent"]
  provider -- recipient suppressed --> mirror["mirror to email_suppression<br/>then raise"]
```

`sendTemplateNow` consults the blocklist before every send. A match returns
`{ status: "suppressed", reason }` and the provider is never contacted , 
the queued worker writes the `notification_delivery` row as `suppressed`
with the reason inlined, and the channel does the same when running
inline.

## Strongest-signal-wins

The local `email_suppression` table keys on the recipient address. The
first verdict wins: once `alice@…` is suppressed by Resend, a later
complaint from SendGrid for the same address is a no-op insert (the
original row stays). The reason this matters: a hard bounce and a spam
complaint should never overwrite each other in either direction. We
keep the strongest signal we already observed and never downgrade a
complaint to a bounce because a later event arrived.

## Configuring the webhooks

Cloudflare needs no wiring, its rejection at send time triggers the
local mirror automatically. Resend and SendGrid each expose a signed
endpoint when their secret is set; without it, the route returns `501`
and the provider's retries park until you configure it.

<CommandRun
  title="Resend"
  caption="point Resend at /api/v1/webhooks/resend with the svix signing secret"
  command={[
    "echo 'RESEND_WEBHOOK_SECRET=whsec_xxxxx' >> compose/.env",
    "# in resend dashboard: Webhooks → Add → https://your-host/api/v1/webhooks/resend",
    "# select events: email.bounced, email.complained",
  ]}
/>

<CommandRun
  title="SendGrid"
  caption="enable the signed event webhook and paste the PEM public key"
  command={[
    "echo 'SENDGRID_WEBHOOK_PUBLIC_KEY=\"-----BEGIN PUBLIC KEY-----...\"' >> compose/.env",
    "# in sendgrid: Settings → Mail Settings → Event Webhook",
    "# url: https://your-host/api/v1/webhooks/sendgrid",
    "# enable 'Signed Event Webhook Requests' and copy the public key",
  ]}
/>

The verification timestamp tolerance is 5 minutes (Resend) / 10 minutes
(SendGrid), outside that window the route returns `401`. Both routes
parse and verify on the raw request body, so reverse proxies must not
mutate the payload.

## Cloudflare visibility

Cloudflare exposes bounce data via the GraphQL Analytics API and the
Email Logs dashboard rather than a webhook. If your operator needs a
real-time signal, point them at
`emailSendingAdaptive` in the Cloudflare GraphQL API. The local
`email_suppression` table covers the practical hot-path concern
(skipping addresses that already bounced); visibility into the
historical event stream lives in Cloudflare's own UI.

## What the operator gets out of the box

- `POST /api/v1/webhooks/resend`, svix-signed bounce / complaint receiver.
- `POST /api/v1/webhooks/sendgrid`, ECDSA-signed event-webhook receiver.
- Suppression check inside `sendTemplateNow`, every send path inherits it.
- Local mirror when the active provider's `send()` returns a
  recipient-level suppression error (Cloudflare today; works the same
  for Resend / SendGrid if their API returns one before a webhook does).
- Automatic clear on email verification.

## Manual operations

For a one-off block (legal request, abuse pattern), insert directly:

```sql
INSERT INTO notifications.email_suppression (email, reason, provider)
VALUES ('user@example.com', 'manual', 'manual')
ON CONFLICT (email) DO NOTHING;
```

To re-enable an address after a verified appeal:

```sql
DELETE FROM notifications.email_suppression WHERE email = 'user@example.com';
```

The next send to that address proceeds normally. If the underlying
issue is unresolved on the provider side, Cloudflare or the webhook
will land a fresh row within the next attempt.
